## 1) Objective And Acceptance Gate
- **Business objective**: When a job fails, users need a clear, actionable error message. Today, pipeline modules raise generic `RuntimeError`/`ValueError`/`FileNotFoundError` that get buried in stack traces. Typed exceptions let the web layer render clean messages and enable future retry logic to discriminate by category.
- **Technical objective**:
  1. Migrate all 22 generic `raise` sites in `pipeline/` to use `FatalError`, `TransientError`, or `DegradedError` from `pipeline/errors.py` — enforcing Architecture Rule 4 "No Silent Failures".
  2. Fix `pipeline/audio.py::has_audio_track` silent failure — ffprobe crashes should raise `FatalError`, not return `False` (which misleads the caller into thinking the video has no audio).
  3. Discriminate Grok HTTP errors: 4xx → `FatalError`, 429/5xx → `TransientError`.
  4. Wrap Demucs GPU+CPU fallback failure in `DegradedError` so callers can eventually skip source separation instead of aborting.
  5. Preserve exact error messages (test substring assertions depend on them).

## 3) Locked Decisions In This Phase
- **Architecture decisions**:
  - **`has_audio_track` keeps bool return for data branches**: returning `True`/`False` when ffprobe runs successfully is semantically correct — "video has / doesn't have audio streams" is data, not an error condition. Only the *inability to determine* (ffprobe crashed) is an operational failure deserving `FatalError`. This gives callers two distinct outcomes they can react to:
    - `has_audio_track == False` → valid video-only file, e.g. silent montage
    - `FatalError` → ffprobe is broken, check installation
  - **`translate.py:185,191` raise `FatalError` after retry exhaustion**: the inline retry loop has already exhausted all attempts × keys. Raising `TransientError` would be dishonest — we stopped trying. If an outer `@retry` decorator is added later, it would double-retry unnecessarily. `FatalError` with "after N attempts" in the message conveys both the retried nature and the final give-up.
  - **`dub/tts.py:125` similarly raises `FatalError`** after `cfg.tts.retry_attempts` attempts — same reasoning.
  - **`grok.py` 4xx vs 5xx discrimination**: 401/403/400 are auth/request bugs that won't be fixed by retrying; 429 is the canonical retryable rate limit; 5xx is transient server-side. Typed exceptions let future `@retry(on=TransientError)` decorator work correctly without string parsing. Net behavior change today: **none** — the inline retry loop in `translate.py:160` still catches `Exception` broadly and inspects via `TranslationProvider.is_rate_limit_error()`.
  - **`dub/separator.py` DegradedError wraps the OUTER path** (including CPU fallback). Inner GPU→CPU retry behavior unchanged. The wrapping creates a single typed exit point so future code can catch `DegradedError(feature="demucs")` and degrade (e.g., switch to `custom_bgm` mode with a warning) instead of aborting the whole job. Current callers (`dub/mixer.py`) don't catch — the `DegradedError` propagates exactly like the old `RuntimeError` did, so behavior is preserved.
  - **`urllib.error.URLError`** (socket/DNS) in `grok.py` was NOT added to the split — it would fall through to the inline retry's `except Exception` at `translate.py:160` unchanged. Scope creep avoided.
- **Config changes**: none
- **API contract changes**: none
- **Error handling policy**: pipeline code now uses typed exceptions exclusively. `RuntimeError`/`ValueError`/`FileNotFoundError` reserved for cases where a standard library actively raises them (e.g., `json.JSONDecodeError` chaining).
- **Why these decisions were chosen**: Architecture Rule 4 "No Silent Failures" + future composability with retry decorator without string parsing.

## 8) Risks, Issues, And Mitigation
- **New risks**:
  - **Grok HTTP error semantics change**: 401 (bad key) now raises `FatalError` instead of falling into inline retry's "wait and try again" path. In the old code, the retry loop caught `Exception`, saw a non-rate-limit error, did exponential backoff, then gave up. Now, the retry loop still catches `Exception` (grok.py's `FatalError` is an `Exception` subclass), still does the backoff... so behavior is actually identical. Long-term impact: if `@retry(on=TransientError)` decorator is introduced, it will NOT retry 4xx — which is the correct semantic.
  - **`has_audio_track` contract change**: third-party consumers of `pipeline.audio.has_audio_track` (if any exist) that relied on silent `False` → see a new exception. Risk: minimal since the function is internal and the only in-tree caller is `extract_audio` which benefits from the fix.
- **Known issues**: none introduced
- **Severity**: low
- **Mitigation in place**:
  - Preserved exact error message substrings to keep test assertions stable
  - Preserved `from e` chaining so `__cause__` traversal works for debugging
  - Inline retry loops left intact — only terminal raise types changed
